# 硬盘（Backblaze）· v3.1 最终结果

代码：**v3.1**，提交 `e35150a`。本次实验在 v3.2 发布之前开始，时间上来不及用 v3.2 重跑。当时使用的代码完整保存在 [`source_runtime/`](source_runtime/)，与 [`session/code_seal.json`](session/code_seal.json) 逐字节一致（仓库根目录现在是 v3.2 代码，和这个封印对不上，这是正常的）。要复现，请先 `git checkout e35150a`，或者直接使用 `source_runtime/`。

数据：Backblaze 2024 年每日硬盘数据，原始 366 个日文件、约 1.05 亿行；186 个基础特征就是数据中的 SMART 原始值和归一化值。

## 结论

| 评估 | 模型 | 故障设备 | TP | FP | FN | 精确率 | 召回率 | **F1** | Accuracy | 平衡准确率 |
|---|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 历史 TEST（2024-10-19 ～ 12-31） | **trial_004** | 804 | 348 | 1,214 | 456 | 22.28% | **43.28%** | **29.42%** | 99.43% | 71.43% |
| 确认窗口（搜索中没有用过） | 基线 trial_001 | 426 | 177 | 836 | 249 | 17.47% | 41.55% | 24.60% | – | – |
| | **trial_004** | 426 | 184 | 851 | 242 | 17.78% | 43.19% | **25.19%** | – | – |
| 训练集 CV（2350 个故障单元） | 基线 trial_001 | – | 716 | 2,555 | 1,634 | 21.89% | 30.47% | 25.48% | – | – |
| | **trial_004** | – | 861 | 2,948 | 1,489 | 22.60% | 36.64% | **27.96%** | – | – |

- TEST 共 292,103 台可评估设备，其中 804 台故障；21,069 台随访未知的设备单独报告，不当作正常设备；
- **只对最终模型做了 TEST**，没有测基线，所以不报告"TEST 上比基线提高了多少"。确认窗口上 F1 从 24.60% 提高到 25.19%，CV 上从 25.48% 提高到 27.96%；
- 确认窗口只保存了汇总指标，没有逐设备表，所以无法计算 Accuracy；
- TEST 时间段在早期是否被使用过无法独立确认，所以不声称这是全新的盲测。本次搜索中 TEST 没有用于选模型、选阈值或反馈给 Agent。

## 亮点

**1. 被采纳的特征完全由特征 Agent 生成。** 分析 Agent 发现很多漏报是"有分数但低于阈值"，请特征 Agent 针对 `smart_187_raw`（报告的不可纠正错误数）写特征。特征 Agent 生成了 4 个因果特征（[`transform.py`](session/feature_programs/b4fd43a30b6952efab2feb31cd67a82379039498f020b8ed9b5e2d2db9b723d9/transform.py)）：

| 特征 | 含义 |
|---|---|
| `fe_187_recent_nonzero_7d_count` | 最近 7 天里，不可纠正错误数非零的天数 |
| `fe_187_recent_increase_7d` | 最近 7 天不可纠正错误数的累计增加量 |
| `fe_187_rolling_mean_7d` | 最近 7 天的平均值 |
| `fe_187_expanding_mean` | 从开始观测到现在的平均值 |

其中 `fe_187_recent_nonzero_7d_count` 成为**模型最重要的特征**（重要性排第一，高于 `smart_197_raw`、`smart_5_raw` 等原始 SMART 指标）。

**2. 没有任何人工编写的特征代码。** 与内存实验不同，硬盘不需要原始日志解析器：基础特征就是数据里的 SMART 列，新增特征全部由 Agent 在受限的特征 API 下生成。这是框架**跨设备类型泛化**最直接的证据。

**3. 连更严格的 v3.1 采纳规则都通过了。** trial_004 的 CV 配对比较：F1 +2.48 个百分点，95% 区间 **[+1.52, +3.47]**，P(更好) = 1.000；新增命中 190 台、丢失命中 45 台。硬盘的 CV 有 2,350 个故障单元，统计证据足够强，所以严格的规则也能采纳真实的提升。这也印证了 v3.2 改规则的理由：v3.1 规则不是错的，而是在故障样本少时（TypeA 约 270、TypeB 只有 34）太保守。

## 如果用 v3.2 会怎样（事后推算）

v3.2 改了两件事，结论不一样：

| v3.2 的改动 | 对硬盘的影响 |
|---|---|
| **采纳规则**：P(更好) ≥ 0.9 且 CV ΔF1 > 0，命中不作否决 | **完全不变**。用 v3.2 规则逐一重新判断 12 次比较，结果和 v3.1 一致：只有 trial_004 被采纳（其余 P(更好) 最高 0.855），最终模型仍是 trial_004 |
| **部署工作点**：改用 CV OOF 选出的轮数和阈值 | **无法评估**。v3.2 会用第 400 轮、阈值 0.98992，v3.1 实际用的是第 550 轮、阈值 0.98748。v3.1 没有保存 `model_full.ubj`，这里也没有原始数据，无法重新预测。内存实验中这个工作点的表现有好有坏（见[采纳规则文档](../../docs/acceptance_rule.md)），所以**不能断定**换成 v3.2 一定更好 |

所以准确的说法是：**换成 v3.2，选出的模型不变；部署工作点的变化可能带来提升，也可能变差，需要实际运行才知道。**（推算用的是同一批 CV 比较结果。重新运行时，Agent 的选择也可能因为大模型的随机性而不同。）

| 部署模型 | 550 棵树，**参数量 15,640**（分裂阈值 + 叶子值），最大深度 4，190 个输入特征，875 KiB |
| 推理时延（只算模型，单核 CPU） | 单条约 0.16 ms；1 万条约 52 ms |
| 步骤级自动化覆盖率 | **98.53%**（67 个自动步骤 / 1 个人工步骤） |
| 实验组级自动化覆盖率 | 100%（13/13） |
| 全流程无人工干预 | **否**（按严格口径） |

**关于那 1 次人工干预：** 会话的第一个事件，就是在任何实验开始之前，把 token 上限从 300 万调低到 150 万（实验组数和调用次数没变）。它的效果等同于在配置文件里设置预算，但按我们的口径（凡是修改预算都算人工干预），还是如实计入。另外，运行中出现过两次资源问题（内存保护中断了第 13 组的 CV，缓存程序因为文件缓存而等待），由人恢复。恢复时没有增加实验、没有修改规则，也没有重新训练最终模型（记录见 [`recovery_20261029/`](recovery_20261029/) 和 `audit/resource_repair_20261029T1738.json`）。这类运行维护操作不属于"修改预算"，按口径不计入，但在这里如实说明。
