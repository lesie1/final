# v3.2：CV 概率采纳规则与 OOF 工作点

## 为什么改

v3.1 在 TypeA、TypeB 各 13 组搜索中都没有采纳任何挑战者，`best` 始终停在基线。只看搜索阶段的证据（CV 和选择窗口），就能看出两个问题：

1. **采纳门槛统计功效不足。** TypeA 的 CV 只有约 272 个故障单元，2 个百分点左右的 F1 提升几乎不可能让配对 bootstrap 的 95% 区间下界大于 0。例如 TypeA trial_011：CV ΔF1 = +2.46 个百分点，优于基线的概率为 0.941，95% 区间为 [-0.84, +5.60]，因此被拒。另外，`new_hits >= lost_hits` 这条否决规则偏向召回：trial_011 主要通过减少误报提高 F1（误报净减少 241 台），却因为丢失命中比新增命中多 10 台而被拒。F1 本身已经同时计入误报和漏报。
2. **部署用的步数和阈值来自故障很少的选择窗口。** TypeA 的选择窗口只有 51 台故障，TypeB 只有 10 台。在这么少的故障上同时挑选训练步数和阈值，验证 F1 会偏乐观：TypeB 基线在不同步数下的验证 F1 从 26% 到 41% 不等，报告值 41% 是其中的最大值，而 CV 估计只有 24%。

**说明：** 修改之前，项目已经看过这些模型的历史 TEST 结果（v3.1 实验快照已从当前目录移除，可在 git 提交 `4c27cf1` 的 `experiments/2026-10-29-memory-v31/report.md` 查看）。上面的理由只依赖 CV 和选择窗口的证据，但 0.9 这个阈值是在看过 TEST 之后才确定的，因此不能把旧测试段上的表现当作新规则的独立证据。新规则的效果应当用新 session 和确认窗口来评价。

## 改了什么

| 项目 | v3.1 | v3.2 默认 |
|---|---|---|
| 采纳检验 `accept_test` | 95% 区间下界 > `accept_lower_bound` | `probability`：P(更好) ≥ `accept_probability`（0.9），且 CV ΔF1 > `accept_lower_bound` |
| 净命中 `accept_require_net_hits` | 必须满足（否决条件） | 只记录，不否决（`false`） |
| 部署工作点 `operating_point` | 选择窗口上的步数和阈值 | `cv_oof`：CV 合并 OOF 选出的步数和阈值 |

旧行为可以通过配置恢复：`accept_test=interval_95`、`accept_require_net_hits=true`、`operating_point=selection_window`。

### OOF 工作点怎么落地

- `xgb_runner.py`：触发早停之后，继续训练到 `cv_rounds` 轮（只训练、不验证，在 GPU 上开销很小），另外保存 `model_full.ubj`。原来的 `model.ubj`（选择窗口上最优的那一步）保持不变，搜索阶段的筛选和诊断仍然使用它。
- `operating_point.py`：`choose(trial_folder)` 返回部署工作点。对于有 CV 结果的单阶段模型，使用 CV 最优步数和 OOF 阈值，并把 `model_full.ubj` 截断到该步数；如果是 rerank/parallel 双分支模型、没有 CV（被筛掉）、或者是旧版本训练的模型，就回退到选择窗口，并写明原因。
- `confirm_search.py`：在确认窗口上**同时**评分两种工作点（`deployed` 和 `selection_window`），这样可以在搜索没有用过的日期上直接比较两种规则。
- `agent.py freeze`：冻结记录中加入 `operating_point`。

**已知假设：** OOF 阈值来自只见过 80% 设备的折模型，用到全量训练模型上时，假设两者的分数尺度相近。确认窗口上的两种工作点对比就是对这个假设的检验。

## 在服务器上重跑

程序文件变了，所以**必须新建 session**，旧 session 和旧结果保持不动。下面的路径来自 v3.1 的配置，请按服务器的实际情况核对。

```bash
cd /root/autodl-tmp
git clone -b cv-operating-point https://github.com/lesie1/final final_v32_20261029   # 慢的话先 source /etc/network_turbo
cd final_v32_20261029
python -m unittest discover -s tests          # 应该全部通过

# TypeA：复用 v3.1 TypeA session 的缓存和冻结采样，新建基线
python search_step.py --initialize-from /root/autodl-tmp/final_v31_20261028/typea/session \
    --session /root/autodl-tmp/final_v32_20261029/typea/session --arm arm_policy.json
python agent.py limits --session /root/autodl-tmp/final_v32_20261029/typea/session --memory-limit-gb 80 --max-trials 13
nohup python agent.py run --session /root/autodl-tmp/final_v32_20261029/typea/session > typea_run.log 2>&1 &

# TypeB：同样复用 v3.1 TypeB session 的缓存
python search_step.py --initialize-from /root/autodl-tmp/final_v31_20261028/typeb/workspace/sessions/20261028_211935_memory_8740df2e \
    --session /root/autodl-tmp/final_v32_20261029/typeb/session --arm arm_policy.json
python agent.py limits --session /root/autodl-tmp/final_v32_20261029/typeb/session --memory-limit-gb 80 --max-trials 13
nohup python agent.py run --session /root/autodl-tmp/final_v32_20261029/typeb/session > typeb_run.log 2>&1 &
```

- 运行前在 shell 中设置 `DEEPSEEK_API_KEY`。如果使用 `TYPEA_SEARCH_ISOLATION`，要确认新 session 目录**不在** `readonly_roots` 里面。
- 内存不够同时跑两个时，先跑 TypeA。v3.1 时一组 13 轮大约需要 4～5 小时。
- 查看进度：`tail -f typea_run.log`，或者 `python agent.py status --session <session>`。
- TypeB 的 v3.1 session 是用 `agent.py init` 建的，这次用 `--initialize-from` 加 arm 策略，部分资源和特征预算设置会和上次不同。所以 v3.2 与 v3.1 的 TypeB 对比不是严格的单因素对比，主要结论应该看**同一个 session 内基线和最优模型的比较**。

搜索结束后：

```bash
python confirm_search.py --session <session> --out <session>/../confirmation
python operating_point.py --trial <session>/trials/<best>/attempt_01      # 查看部署工作点
```

如果需要在已授权的 TEST 上评估，冻结和预测脚本应该用 `operating_point.choose()` 和 `operating_point.load()` 得到的模型和阈值，不能直接用 `result.json` 里的 `metrics.threshold`。
